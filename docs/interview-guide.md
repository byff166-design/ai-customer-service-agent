# 面试讲解稿

## 30 秒项目介绍

我开发了一个基于 Spring Boot 和 LangChain4j 的电商智能客服系统。它不是让模型直接回答订单信息，而是通过 Function Calling 选择订单、物流、FAQ、工单和转人工工具，由 Java 业务层查询 H2 数据库并执行规则。项目还实现了 TraceId 与 JSON 日志、会话摘要持久化、工具调用审计、异常降级和 40 项自动测试。

## 高频追问

### Function Calling 和普通 Prompt 有什么区别？

普通 Prompt 只能要求模型输出文本；Function Calling 会把工具名称、说明和参数结构提供给模型。模型返回需要调用的工具及参数，Java 程序执行后再把结果交给模型。因此真实业务数据和权限仍由后端控制。

### 为什么还需要 mock 模式？

真实模型调用存在费用、网络和非确定性，不能作为 CI 的唯一依据。mock 模式和 AI 模式复用相同工具与数据库，只替换意图决策层，因此能稳定测试业务闭环，同时保留真实模型演示能力。

### 如何防止模型幻觉？

订单、物流和工单信息必须通过工具获取；缺少参数先追问；工具失败或 FAQ 无依据时明确不知道并转人工。模型没有数据库访问权限，也不能绕过业务 Service。

### 如何避免重复工单？

创建工单前先校验订单存在，再按 `orderNo + OPEN` 查询正在处理的工单。如果存在就抛出业务异常并返回已有工单号。生产环境还应增加数据库唯一约束或幂等键解决并发竞争。

### ThreadLocal 有什么风险？

线程池会复用线程，所以必须在 `finally` 中调用 `remove()`。当前链路是同步请求；若未来切换到异步或响应式调用，应改用显式上下文传递或 Reactor Context。

### TraceId 如何贯穿整条链路？

入口 Filter 校验并接收上游 `X-Trace-Id`，没有则生成新值；随后写入 ThreadLocal 和 MDC，响应头及聊天响应体回传同一个值。工具审计入库也保存该 TraceId，因此可以从一次接口响应定位到 JSON 日志和数据库记录。Filter 在 `finally` 中清理上下文，避免线程复用造成串号。

### 为什么结构化日志使用 JSON？

普通文本适合人工阅读，但不利于聚合统计。项目把事件、模式、会话、耗时和调用结果作为固定字段输出，可以计算 LLM 耗时、工具成功率和转人工率。当前输出到控制台；生产环境可由日志采集器发送到 Loki、ELK 等平台。

### 摘要记忆如何避免无限增长？

短期消息保留在窗口中，达到阈值后选择完整的旧对话轮次交给独立摘要器压缩，只保留最近消息。摘要写入 H2，应用重启后仍能恢复。摘要作为受限系统上下文注入，不允许覆盖客服安全规则。当前使用 sessionId 区分会话，真正跨设备画像必须增加登录和 customerId。

### 为什么 MVP 不上 Redis、MQ、RAG？

这个项目要突出 Tool Calling 和工单闭环。RAG 已经在另一个知识库项目展示，继续堆相同技术会稀释主题。Redis、MQ 应在出现分布式会话或异步工单需求后再引入，而不是为了简历关键词强行增加。
