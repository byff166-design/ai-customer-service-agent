# 面试讲解稿

## 30 秒项目介绍

我开发了一个基于 Spring Boot 和 LangChain4j 的电商智能客服系统。它不是让模型直接回答订单信息，而是通过 Function Calling 选择订单、物流、FAQ、工单和转人工工具，由 Java 业务层查询 H2 数据库并执行规则。项目还实现了工具调用审计、重复工单校验、异常降级和 33 项自动测试。

## 高频追问

### Function Calling 和普通 Prompt 有什么区别？

普通 Prompt 只能要求模型输出文本；Function Calling 会把工具名称、说明和参数结构提供给模型。模型返回需要调用的工具及参数，Java 程序执行后再把结果交给模型。因此真实业务数据和权限仍由后端控制。

### 为什么还需要 mock 模式？

真实模型调用存在费用、网络和非确定性，不能作为 CI 的唯一依据。mock 模式和 AI 模式复用相同工具与数据库，只替换意图决策层，因此能稳定测试业务闭环，同时保留真实模型演示能力。

### 如何防止模型幻觉？

订单、物流和工单信息必须通过工具获取；缺少参数先追问；工具失败或 FAQ 无依据时明确不知道并转人工。模型没有数据库访问权限，也不能绕过业务 Service。

### 如何避免重复工单？

创建工单前先校验订单存在，再按 `orderNo + OPEN` 查询正在处理的工单。如果存在就抛出业务异常并返回已有工单号。生产环境还应增加数据库唯一约束或幂等键解决并发竞争。

### ThreadLocal 有什么风险？

线程池会复用线程，所以必须在 `finally` 中调用 `remove()`。当前链路是同步请求；若未来切换到异步或响应式调用，应改用显式上下文传递或 Reactor Context。

### 为什么 MVP 不上 Redis、MQ、RAG？

这个项目要突出 Tool Calling 和工单闭环。RAG 已经在另一个知识库项目展示，继续堆相同技术会稀释主题。Redis、MQ 应在出现分布式会话或异步工单需求后再引入，而不是为了简历关键词强行增加。
